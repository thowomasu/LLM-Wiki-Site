Two Current Cross-Dataset Pipelines

This page compares the strict time-domain-to-EIS validation lane with the newer missing battery measurement prediction lane. Both use multiple datasets. Only one currently has the better development outlook.

Download readiness JSON Download transfer results Download final LiFePO4 results

Executive Read

The time-domain-to-EIS pipeline is the stricter validation lane, and it currently says no_support. That is not a disaster. It means the pipeline caught a weak model instead of letting us overclaim.

The missing battery measurement prediction pipeline is the better current development bet. It is operational, it uses more of the available data, and some heads beat their grouped baselines. But it is still development evidence, not a clean external validation claim.

Best one-line meeting answer

We built two cross-dataset tracks. The strict EIS prediction validation track failed honestly. The missing measurement prediction track is the more promising direction for the next two weeks.

What not to say

Do not say the learned time-domain-to-EIS model is validated. Do not say pseudo-labels are measurements.

What to say instead

The current work is progress in pipeline design and dataset discipline. The next bottleneck is stronger held-out complete data, not just a fancier model.

Question

Which cross-dataset pipeline is stronger right now, and which one has the better two-week development outlook?

Pipeline A: Time-domain to EIS

Predict measured EIS spectra from time-domain diagnostic features. This is a hard, direct generalization problem.

Pipeline B: Missing battery measurement prediction

Use time-series, EIS, and RPT/SOH when available, then estimate missing measurements with uncertainty labels.

Side-By-Side Comparison

Category Pipeline A: Time-Domain to EIS Pipeline B: Missing-Modality Transfer
Main goal Predict fixed-grid EIS targets from current and voltage diagnostic features. Fill missing EIS or RPT/SOH-style outputs when a dataset has only part of the measurement set.
Current verdict No support. Final LiFePO4 validation did not support the learned model. Best development bet. Operational transfer pipeline with supported heads, but not final validation.
Why it matters It is the stricter honesty check. It prevents us from pretending a weak model generalizes. It is more flexible. It can learn from datasets that do not all contain the same measurements.
Dataset coverage Cleaned v2 development data uses 3 defensible datasets: DIB spent validation, repaired RADAR4KIT, and Stanford SECL. Registry loads 5 dataset groups: DIB, LiFePO4 HEV, Molicell P42A, repaired RADAR4KIT, and Stanford SECL.
Scale Cleaned v2 has 618 rows. LiFePO4 final kept-back test has 198 scored rows. Transfer registry has 917 rows. Current report writes 634 pseudo-label rows.
Best evidence Some development folds beat baseline, but not all. The final run only froze a global-mean negative-control baseline. Ohmic-proxy EIS head beats baseline on 5 of 5 grouped folds. Dataset-relative RPT heads beat baseline on 2 of 2 grouped folds.
Weakest point The learned model is not stable enough across datasets. It loses the right to be called validated. Pseudo-labels are estimates, not measurements. The all-three-modality evidence is still too thin.
Meeting framing We built the strict lane, ran it, and it gave a negative result. That is useful and honest. We built the broader lane that looks more promising for continued development, as long as we keep the limit of the evidence visible.
Two-week outlook Low to medium. Keep it as a baseline and validation guardrail. Do not tune it after failure to chase a win. Medium to high. Freeze the promising heads, improve comparable test workflows, and find another complete held-out battery.
Current ranking Second. Better as an honesty check than as the main research bet right now. First. Better near-term path because it has more usable signal and more ways to improve without faking validation.

Recommendation

Lead with the honest negative

The strict time-domain-to-EIS validation lane did not support the learned model. This is a real result, not a failure to hide.

Shift the next two weeks toward missing measurement prediction

It has the better development surface: more datasets, more measurement combinations, and supported heads that can be frozen before future testing.

Do not inflate pseudo-labels

Pseudo-EIS and pseudo-RPT are estimates. Treat them as lower-trust development labels until a future held-out complete battery tests the frozen heads.

Ask for better data, not just more modeling

The next bottleneck is a cleaner complete dataset with time-series, EIS, and RPT/SOH labels. Without that, model polish will mostly make the story prettier, not truer.

Claim Boundary

Defensible claim: we now have two cross-dataset battery pipelines. One strict validation lane found no support for the learned time-domain-to-EIS model. The newer missing-modality lane is the stronger near-term development direction.

Not defensible: claiming the time-domain-to-EIS model is externally validated, or treating pseudo-labels as measured EIS/RPT values.
